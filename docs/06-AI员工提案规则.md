# 06 AI 员工提案规则

三个 AI 员工在每个季度开始时各给一份完整的方案。方案是按下面的固定规则算出来的，不是大模型生成的。代码放在 `src/staff/`，只能引用 `engine`、`params`、`products`。

这一点必须在游戏里写明（见 `docs/07` 第 6.5 节）。

## 一、三个人

三个员工直接用职务称呼，不另外起名字。

| 代号 | 称呼 | 偏向 |
|---|---|---|
| `purchase` | 采购 | 最怕缺货和违约。多进货，大单只接交得出的 |
| `ops` | 运营 | 只看单量。降价、加出价、所有大单都抢 |
| `finance` | 财务 | 保守。少花钱，重视合规 |

## 二、一份方案里有什么

```ts
interface Proposal {
  staff: "purchase" | "ops" | "finance";
  decision: QuarterDecision;          // 完整的决定，见 docs/04 第 2.2 节
  forecast: {
    retailOrders: number;             // 他预测这个季度零售发出多少单
    quarterEndCashFen: number;        // 他预测季度结束时有多少现金
  };
  reasons: { key: string; data: Record<string, number> }[];   // 理由。只带编号和数字，文字在 src/text
}
```

玩家把决定分成四组，每一组可以选一个人的，也可以自己填：

| 组 | 包含 |
|---|---|
| 进货 | `monthlyRestockQty` |
| 零售 | `priceSen`、`adBidFen`、`adDailyBudgetFen` |
| 大单 | `bulkQuotes` |
| 风险 | `buyCompliance`、`upgradeToLocal` |

也可以一键"全部听某一个人的"。

## 三、三个人都要用到的数

```
seasonNowBp  = applyBp(product.seasonBp[season], year === 0 ? 10000 : year2DemandBp)

expMonthly =                                          // 预计这个季度每个月零售来多少单
  第 0 个季度：Math.floor(Math.floor(product.organicPerDayMilli * 30 / 1000) * seasonNowBp / 10000)
  其他季度：  Math.floor(Math.floor(上个季度的 quarterStats.wanted / 3) * seasonNowBp / 上个季度的 seasonNowBp)

refBidFen    = 这个季度的对手出价（docs/04 第四节，没有每天的波动）

roundUp10(x) = x <= 0 时是 0；否则 Math.max(product.moq, Math.ceil(x / 10) * 10)

canDeliver(inquiry, restockQty) =                     // 这张大单交不交得出
  offset   = shipDay - 季度第一天
  arrivals = 这个季度的三次月初补货（偏移 0、30、60）里，到货偏移不大于 offset 的次数
             （到货偏移 = 补货偏移 + supplierLeadDays，本土店再加 headHaulDays）
  stockQty + arrivals * restockQty - Math.ceil(expMonthly * offset / 30) >= inquiry.qty
```

## 四、每个人的方案

### 采购

| 项目 | 规则 |
|---|---|
| 每月补货量 | `Math.min(supplierMonthlyCap, roundUp10(Math.ceil(expMonthly * purchaseStockBp / 10000) + Math.ceil(这个季度所有询价单的件数之和 / 3)))` |
| 售价、广告 | 保持现在的值不变 |
| 大单 | 按询价单的顺序，`canDeliver` 成立的就报 `bulkRefPriceSen`，不成立的不报 |
| 合规、升级 | 都是 `false` |

### 运营

| 项目 | 规则 |
|---|---|
| 每月补货量 | `Math.min(supplierMonthlyCap, roundUp10(expMonthly))` |
| 售价 | 推流分总分低于 `opsPushTarget`：参考价减一档（不低于最低价）。否则是参考价 |
| 广告出价 | `applyBp(refBidFen, opsBidBp)` |
| 每日预算 | `Math.min(applyBp(Math.max(0, cashFen), opsBudgetBp), 出价 * adClickPoolPerDay)` |
| 大单 | 全部报价，`applyBp(bulkRefPriceSen, opsQuoteBp)` |
| 合规 | `false` |
| 升级 | 跨境直发、不是第 0 个季度、并且 `cashFen >= 2 * localSetupFeeFen` 时是 `true` |

### 财务

| 项目 | 规则 |
|---|---|
| 每月补货量 | 取两个数里小的：`roundUp10(Math.ceil(expMonthly * financeStockBp / 10000))`，和 `Math.floor(applyBp(Math.max(0, cashFen), financeStockCashBp) / costFen / 10) * 10`。结果低于起订量就是 0 |
| 售价 | 参考价 |
| 广告出价 | `applyBp(refBidFen, financeBidBp)` |
| 每日预算 | `Math.min(applyBp(Math.max(0, cashFen), financeBudgetBp), 出价 * adClickPoolPerDay)` |
| 大单 | 只报同时满足两条的：`qty * costFen <= applyBp(Math.max(0, cashFen), financeBulkCashBp)`；`canDeliver` 成立。报价是 `applyBp(bulkRefPriceSen, financeQuoteBp)` |
| 合规 | 本土店并且风险等级不是"低"时是 `true` |
| 升级 | 跨境直发、已经到第二年、并且 `cashFen >= 4 * localSetupFeeFen` 时是 `true` |

## 五、预测

每个人的预测这样算：

1. 用他自己的完整方案，从现在的状态往下试算一个季度（调用 `startQuarter`，再调用 `stepDay` 直到过完 90 天）。试算时遇到要玩家选择的地方（`docs/04` 第十六节），一律当作"不处理"。得到真实的零售发出单数和季度末现金。试算不改变真正的游戏状态。
2. 乘上他的偏差。偏差每个季度不同，用 `dayRng(seed, q, stream).int(最小, 最大)` 取：

| 员工 | `stream` | 零售单数的偏差 | 季度末现金的偏差 |
|---|---|---|---|
| 采购 | 8 | `purchaseOrderBiasMinBp` 到 `purchaseOrderBiasMaxBp` | 不偏 |
| 运营 | 9 | `opsOrderBiasMinBp` 到 `opsOrderBiasMaxBp` | `opsCashBiasMinBp` 到 `opsCashBiasMaxBp` |
| 财务 | 10 | `financeOrderBiasMinBp` 到 `financeOrderBiasMaxBp` | `financeCashBiasMinBp` 到 `financeCashBiasMaxBp` |

先取单数的偏差，再取现金的偏差。现金是负数时不乘偏差。试算中途倒闭或被封店的，照样报告当时的数字，并加一条理由 `plan_ends_game`。

## 六、季度结束时的对账

季度结束后显示三行，每个人一行：

| 内容 | 怎么算 |
|---|---|
| 他当时预测的 | 第五节的 `forecast` |
| 如果全部听他的，实际会怎样 | 第五节第 1 步试算出来的真实数字（没有乘偏差） |
| 你实际的结果 | 这个季度真正的零售单数和季度末现金 |

再记下玩家每一组听了谁的，累计到结局用：

```ts
interface TrustStats {
  adopted: Record<"purchase" | "ops" | "finance" | "self", number>;   // 四组决定里各听了几次
  overForecast: Record<"purchase" | "ops" | "finance", number>;       // 他的预测单数高于"全部听他的"的真实单数，有几个季度
}
```

## 七、理由的编号

每份方案带 1 到 3 条理由。编号和触发条件：

| 员工 | `key` | 什么时候给 | 带的数字 |
|---|---|---|---|
| 采购 | `purchase_season_up` | 这个季度的 `seasonNowBp` 比上个季度高 | 两个季度的倍数 |
| 采购 | `purchase_stock_days` | 总是给 | 现有库存够卖几天（`stockQty * 30 / expMonthly`，向下取整） |
| 采购 | `purchase_bulk_cannot` | 有询价单他没报 | 那张单的件数、缺多少件 |
| 运营 | `ops_push_low` | 推流分低于 `opsPushTarget` | 推流分总分 |
| 运营 | `ops_rival_bid` | 总是给 | 对手出价、他的出价 |
| 运营 | `ops_grab_all` | 有询价单 | 询价单张数、总件数 |
| 财务 | `finance_cash_low` | 采购或运营的方案试算出来季度内现金最低点低于 `financeCashWarnFen` | 是谁的方案、最低点是多少 |
| 财务 | `finance_risk` | 本土店并且风险等级不是"低" | 风险等级 |
| 财务 | `finance_balance_late` | 有询价单 | 尾款要等多少天 |
| 三个人 | `plan_ends_game` | 自己的方案试算时倒闭或被封店 | 发生在第几天 |

## 八、参数

加进 `src/params/malaysia.ts`，全部是等级 C。

| 名称 | 值 | 单位 | 说明 |
|---|---|---|---|
| `purchaseStockBp` | 13000 | bp | 采购按预计销量的 1.3 倍进货 |
| `opsPushTarget` | 70 | 分 | 推流分低于这个数，运营就要降价 |
| `opsBidBp` | 12000 | bp | 运营出对手的 1.2 倍 |
| `opsBudgetBp` | 200 | bp | 运营每天最多花现金的 2% |
| `opsQuoteBp` | 9300 | bp | 运营按批发参考价的 93% 报价 |
| `financeStockBp` | 9000 | bp | 财务按预计销量的 0.9 倍进货 |
| `financeStockCashBp` | 2500 | bp | 财务一次进货不超过现金的四分之一 |
| `financeBidBp` | 8000 | bp | 财务出对手的 0.8 倍 |
| `financeBudgetBp` | 50 | bp | 财务每天最多花现金的 0.5% |
| `financeBulkCashBp` | 4000 | bp | 一张大单的货款超过现金的四成，财务不接 |
| `financeQuoteBp` | 10500 | bp | 财务按批发参考价的 105% 报价 |
| `financeCashWarnFen` | 50000 | fen | 现金最低点低于 ¥500，财务发出警告 |
| `purchaseOrderBiasMinBp` / `purchaseOrderBiasMaxBp` | 10500 / 12500 | bp | 采购高估销量 |
| `opsOrderBiasMinBp` / `opsOrderBiasMaxBp` | 11000 / 14000 | bp | 运营高估销量 |
| `opsCashBiasMinBp` / `opsCashBiasMaxBp` | 10500 / 12000 | bp | 运营高估现金 |
| `financeOrderBiasMinBp` / `financeOrderBiasMaxBp` | 8000 / 9500 | bp | 财务低估销量 |
| `financeCashBiasMinBp` / `financeCashBiasMaxBp` | 8500 / 9800 | bp | 财务低估现金 |

## 九、要写的函数

| 函数 | 作用 |
|---|---|
| `expectedMonthly(state, product, params)` | 第三节的 `expMonthly` |

## 十、核对用例

头巾，第 0 个季度，跨境直发。状态：`cashFen` 320000，`stockQty` 200，推流分总分 65，售价 1990，广告出价和预算都是 0。这个季度有一张询价单：300 件，`dueDay` 60。

先算出：`seasonNowBp` 22000，`expMonthly` 264，`refBidFen` 36，大单的 `shipDay` 是 50。

说明：真实的游戏里第 0 个季度没有询价单（`bulkStartQuarter` 是 1）。这条用例是为了核对规则，测试时直接构造一个带询价单的状态。

| 员工 | 每月补货量 | 售价 | 广告出价 | 每日预算 | 大单 |
|---|---|---|---|---|---|
| 采购 | 450 | 1990 | 0 | 0 | 报 1050（两次补货在第 50 天前到货：200 + 900 − 440 = 660，够 300） |
| 运营 | 270 | 1890 | 43 | 6400 | 报 977 |
| 财务 | 80 | 1990 | 29 | 1600 | 不报（货款 270000 分，超过现金的四成 128000 分） |

另外要测试：

1. 三个人的方案都是合法的 `QuarterDecision`（用 200 个种子、每个季度都检查）。
2. `dryRunQuarter` 不改变传进去的状态。
3. 同一个状态算两次，三份方案完全相同。
4. 全部听某一个人的，真正跑完这个季度，结果和他的试算完全相同。
