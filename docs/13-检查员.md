# 13 检查员

这份文档规定：开发过程中，谁来盯着"做完了没有、做对了没有"。`docs/11` 规定检查什么；本文规定检查怎样自动发生、由谁来下结论。

**写代码的和下结论的不能是同一个。** 写代码的助手自己说"做完了"不算数。下面四样都过了，一个任务才算完成。

## 一、四样东西

| 名字 | 是什么 | 什么时候动 | 谁启动 |
|---|---|---|---|
| 自动检查 | 一条命令 `npm run check`，把能用程序查的全部查一遍 | 每次改完代码 | 写代码的助手 |
| 自动拦截 | 两个钩子：提交之前、助手停下来之前，自动运行自动检查，不通过就拦住 | 自动 | 没有人，自己动 |
| 页面自检 | 页面角落的一个小面板，实时检查画面有没有违反 `docs/08` | 打开开发用的页面时 | 自己动 |
| 检查员 | 另一个独立的 AI 智能体，查程序查不了的，写检查记录，下结论 | 每个任务（或任务里的一步）做完并提交之后 | 写代码的助手调用它 |

前三样是程序，由写代码的助手在任务 01 和任务 06 里按本文做出来。第四样的定义文件已经在项目里：`.qoder/agents/inspector.md`。

## 二、自动检查

### 2.1 命令

| 命令 | 查哪些 | 要求 |
|---|---|---|
| `npm run check` | K1 到 K5 | 目标是 60 秒之内跑完。超过了不要减少测试，把最慢的几条测试报告出来 |
| `npm run check:full` | K1 到 K8 | 任务或一步做完时运行 |
| 后面加 `-- --task 03` | 同上，并且把任务 01 到 03 应该有的核对用例都当作必须有 | 检查员用 |
| 后面加 `-- --accept` | 全部通过时，把现在通过的测试条数记进基线 | 只有检查员用 |

脚本放在 `scripts/check/`，用 Node 直接运行（`.mjs` 文件），不为它新增依赖。

### 2.2 查什么

| 编号 | 名字 | 怎么查 | 从哪个任务开始有 |
|---|---|---|---|
| K1 | 规则包没有被改 | 读 `规则包清单.sha256`。里面每一行是一个文件的 SHA-256 和路径。重新算一遍，有一个不一样就不通过，并列出是哪个文件 | 01 |
| K2 | 类型检查 | `tsc --noEmit` | 01 |
| K3 | 测试 | `vitest run`。全部通过，没有被跳过的。规则检查（`docs/11` 的 R1 到 R10）也在这里面 | 01 |
| K4 | 测试没有变少 | `tests/` 里没有 `.skip`、`.only`、`.todo`、`xit`、`xdescribe`；通过的条数不少于 `检查记录/基线.json` 里记的数 | 01 |
| K5 | 核对用例齐全 | 见 2.3 | 01 |
| K6 | 打包和体积 | `vite build` 成功；`dist/` 里的 JS 压缩（gzip）后合计不超过 600 KB | 01 |
| K7 | 画面 | `npm run shots`，`docs/11` 第 4.2 节的 S1 到 S14 | 06 |
| K8 | 模拟报告是最新的 | 重新运行 `npm run sim`，生成的内容和已经提交的 `模拟报告.md` 完全一样 | 04 |

- 每一项都要运行，前面的不通过也接着查后面的。
- 还没有做到的项目（例如任务 03 时的 K7）显示"还没有"，不算不通过。
- `规则包清单.sha256` 里以 `#` 开头的行是说明，第一行写着规则包是第几版。K1 把这个版本号显示出来。

### 2.3 核对用例齐全（K5）

文档里的核对用例，一条对应一个测试。测试的名字必须以方括号里的编号开头：

```
[G03-10.1#01] C1 跨境直发 RM20.00 100 克 西马
```

- `G03-10.1` 是这一组的编号，`#01` 是表格里从上到下的第几行，两位数。
- 有哪些组、每组几条，写在 `docs/核对用例清单.json`。脚本读这个文件，不要另外抄一份。
- K5 的判断：一组里一条都没有，显示"还没有"；有但不够数，或者有没通过的，不通过。加了 `--task` 时，任务编号不大于它的组必须齐。
- 核对用例的测试里，期望的数字要直接写出来，和文档一字不差。不能用被测的函数自己算出期望值。

| 组 | 出处 | 条数 | 任务 |
|---|---|---|---|
| `G03-10.3` | `docs/03` 第 10.3 节，`money.ts` | 17 | 01 |
| `G03-5` | `docs/03` 第五节，跨境运费 | 13 | 02 |
| `G03-10.1` | `docs/03` 第 10.1 节，`settleOrder` | 11 | 02 |
| `G03-10.2` | `docs/03` 第 10.2 节，`unitProfit` | 4 | 02 |
| `G05-4` | `docs/05` 第四节，六种商品两种发货方式 | 12 | 03 |
| `G04-14.1` | `docs/04` 第 14.1 节，推流分 | 3 | 03 |
| `G04-14.2` | `docs/04` 第 14.2 节，广告 | 9 | 03 |
| `G04-14.3` | `docs/04` 第 14.3 节，5 条价格系数加 1 条自然订单 | 6 | 03 |
| `G04-14.4` | `docs/04` 第 14.4 节，B1 到 B3 加 1 条 B2 的后续 | 4 | 03 |
| `G04-14.5` | `docs/04` 第 14.5 节，4 条进货价格加 1 条仓储费 | 5 | 03 |
| `G04-15` | `docs/04` 第十五节，加急补货 | 2 | 03 |
| `G06-10` | `docs/06` 第十节，采购、运营、财务各一条，每条检查 5 个数 | 3 | 05 |

"必须成立的关系"那一类测试（`docs/03` 第 10.4 节、`docs/04` 第 14.6 节和第十五节）不在这张表里，由检查员看（第 5.6 节）。

### 2.4 输出

终端里每一项一行，最后一行是总的结果：

```
K1 规则包没有被改（第 1 版）   通过
K2 类型检查                   通过
K3 测试（86 条）              通过
K4 测试没有变少（基线 86）     通过
K5 核对用例齐全（4 组齐，8 组还没有）  通过
自动检查：通过
```

- 不通过的项目，下面打印原因，最多 30 行。
- 有一项不通过，命令的退出码就不是 0。
- 同时把结果写进 `检查记录/自动/最新.json`：当前提交的编号、有没有未提交的改动、规则包的版本、每一项的结果、通过的测试条数。这个文件不提交（写进 `.gitignore`）。

## 三、自动拦截

### 3.1 提交之前

- `.githooks/pre-commit` 运行 `npm run check`。不通过，这次提交就不成功。
- `package.json` 里加 `"prepare": "git config core.hooksPath .githooks"`，这样运行 `npm install` 之后钩子就生效。
- 不允许用 `git commit --no-verify` 绕过。

### 3.2 助手停下来之前

用 Qoder 的 Hooks 功能：助手每次要结束回答时，自动运行一个脚本；脚本说不行，助手就得接着干。

脚本 `scripts/check/stop-hook.mjs` 要做的事：

1. 读标准输入里的 JSON。里面的 `stop_hook_active` 是 `true` 时，直接放行。这样每次停下来最多只拦一次，不会没完没了。
2. `src/`、`tests/`、`scripts/` 里没有未提交的改动时，放行（已经提交的，提交之前查过了）。
3. 运行 `npm run check`。通过就放行。
4. 不通过：把没通过的项目和原因写到标准错误，最后加上下面这句话，用退出码 2 结束。

```
自动检查没有通过，请修好再停。如果你停下来是因为要问项目负责人问题，把问题和现在没通过的项目写清楚，然后可以停。
```

配置写在 `.qoder/settings.json`，事件是 `Stop`，超时设为 120 秒（超时算放行）。脚本不依赖 `jq`。改了配置要重启 Qoder 才生效。

上面的做法是按 Qoder 国际版的官方文档写的。**你所在的版本如果不一样，以你那个版本的官方文档为准。如果不支持 Hooks，如实说出来，不要假装配好了**；那样就只靠 3.1。

## 四、页面自检

把 `docs/11` 第 4.2 节里能在页面里量出来的检查，写成一组函数，放在 `src/ui/dev/selfcheck.ts`。

| 检查 | 内容 |
|---|---|
| S1 | 没有左右滚动 |
| S3 | 没有小于 12 像素的文字 |
| S4 | 窗口宽度小于 768 时，按钮和输入框的点击区域不小于 44 × 44 |
| S7 | 没有文字超出自己的框 |
| S12 | 世界里的小牌子互相不重叠，也不盖住三个角色 |
| S13 | 时间线、状态、询价、前排、决定栏这五个区互相不重叠 |
| S14 | 画面上只有一个主要按钮（弹窗打开时，弹窗后面的不算） |

- 网址里有 `debug`、`demo`、`gallery` 任何一个参数时，页面提供 `window.__selfcheck()`，返回每一项的编号、是否通过、不通过的是哪个元素。
- 截图脚本（`npm run shots`）直接调用它，不另外写一遍。同一套检查，两处用。
- `?debug=1` 时，角落的小面板除了现金等式，再加一行"自检 7/7"。有不通过的就变红，点开能看到是哪一项、哪个元素。
- 什么时候重新查：换阶段、开关弹窗、窗口大小变化；播放时每秒一次。
- 为了能查，下面这些元素要带标记：五个区 `data-region="timeline"`、`"status"`、`"inquiry"`、`"cast"`、`"decide"`；主要按钮 `data-primary`；世界里的小牌子 `data-world-label`；三个角色 `data-cast`。

## 五、检查员

### 5.1 是谁

一个独立的 AI 智能体，定义在 `.qoder/agents/inspector.md`。它有自己的对话，看不到写代码的助手说过什么，只看代码、文档和命令的输出。

- 能做：读所有文件；运行命令；在 `检查记录/` 里写文件。
- 不能做：修改 `检查记录/` 之外的任何文件；替写代码的助手修问题；改文档。

### 5.2 什么时候查

下面每一行做完、`npm run check:full` 通过、并且已经提交之后，查一次：

| 任务 | 查几次 |
|---|---|
| 01、02、04、05、07、08、09 | 每个任务做完查一次 |
| 03 | 三步，每一步做完查一次 |
| 06 | 三步，每一步做完查一次。检查员通过之后，还要等项目负责人看过截图 |

### 5.3 怎么叫它

写代码的助手做完一步并提交之后，自己调用检查员，只说一句话，不加任何解释：

```
检查任务 03 第 2 步。
```

如果所在的版本不能调用自定义智能体，写代码的助手要如实说出来。这时由项目负责人开一个新对话，说：

```
请读 .qoder/agents/inspector.md，你现在就是里面说的检查员。检查任务 03 第 2 步。
```

### 5.4 检查的步骤

1. 读 `AGENTS.md`、本文、`docs/11`、要检查的任务文件，以及任务文件开头列出的文档。
2. 看改了什么：`git status`（应该是干净的）；`git log`；从进度表里上一次通过的提交到现在的 `git diff --stat`。
3. **自己运行** `npm run check:full -- --task 任务编号`。不用写代码的助手贴出来的结果。
4. 任务文件里"测试"和"完成的标准"每一条，逐条给出结果：通过、不通过、查不了。每一条都要有证据。
5. 过一遍第 5.5 节的通用清单。
6. 过一遍第 5.6 节里这个任务的重点。
7. 界面的任务：看 `过程截图/自动/` 里的截图，和 `参考图/` 对照（第七节）。看不了图片就写"查不了"。
8. 按第 5.7 节写检查记录，更新进度表（第六节）。
9. 结论是通过时，运行 `npm run check:full -- --task 任务编号 --accept`。
10. 最后运行 `git status`，确认自己只动了 `检查记录/`，然后把 `检查记录/` 提交一次，格式是 `chore: 检查记录 任务 03 第 2 步 第 1 次（通过）`。

证据是指：文件路径加行号，或者命令的真实输出。没有证据的结论不要写。

### 5.5 通用清单

每次都查。这些是程序查不出来、AI 写代码时又最容易出的问题。

| 编号 | 查什么 | 怎么查 |
|---|---|---|
| T1 | 只做了任务里写的事 | 对照任务文件看 `git diff --stat`。有没有多出来的功能、文件、依赖（看 `package.json` 的变化） |
| T2 | 没有改不该改的 | `docs/`、`AGENTS.md`、`参考图/`、`规则包清单.sha256`、`.qoder/agents/` 没有变；以前任务的测试被改了的，`开发日志.md` 里要有理由 |
| T3 | 测试是真的在测 | 核对用例的期望值和文档逐个数字对比：一组不到 20 条的全部对，更多的至少抽 10 条。没有空的测试，没有 `expect(true)`，期望值不是被测函数自己算的 |
| T4 | 代码是按文档的算法写的，不是凑出来的 | 读实现。没有针对某个核对用例输入的特殊处理；计算的顺序、取整的方式和文档一致 |
| T5 | 业务数字都来自参数表 | `src/engine`、`src/staff` 里没有直接写的费率、天数、金额 |
| T6 | 界面上的数字都来自计算 | 组件里没有写死的金额、件数、百分比。`?demo=` 的固定状态也是用模型算出来的，不是手写的假数据 |
| T7 | 没有假装完成 | 没有 `TODO`、`FIXME`、空的函数、大段被注释掉的代码、留下的 `console.log`、把错误吞掉的 `try/catch` |
| T8 | 记录如实 | `开发日志.md` 写的和 git 里实际改的一致；报告里的测试条数和自己运行的一致 |
| T9 | 没有密钥、没有真实平台的名字、没有网络请求 | 搜索整个项目（不含 `node_modules`） |
| T10 | 检查本身没有被改松 | 看 `scripts/check/`、`.githooks/`、`.qoder/settings.json`、规则检查的测试、`src/ui/dev/selfcheck.ts` 的变化。少查了东西、放宽了条件的，算一级问题 |
| T11 | 分层没有被破坏 | `docs/01` 第四节。重点看 `src/ui` 有没有绕过 `store/actions.ts` 和 `store/selectors.ts` |

### 5.7 检查记录

文件放在 `检查记录/`，名字是 `任务03-步2-第1次.md`（没有分步的任务是 `任务02-第1次.md`）。格式：

```
# 检查记录：任务 03 第 2 步，第 1 次

- 检查的提交：abc1234
- 规则包：第 1 版
- 结论：通过 / 不通过（一级 0 条，二级 2 条，三级 1 条）

## 一、自动检查
（自己运行 npm run check:full 的真实输出）

## 二、任务文件里的每一条
| 哪一条 | 结果 | 证据 |

## 三、通用清单
| 编号 | 结果 | 证据 |

## 四、这个任务的重点
| 重点 | 结果 | 证据 |

## 五、问题
| 编号 | 级别 | 在哪 | 是什么 | 证据 |

## 六、拿不准的和查不了的（留给项目负责人）

## 七、文档的问题（留给文档的作者）
```

问题的级别按 `docs/11` 第六节。

### 5.8 结论怎么下

同时满足下面三条才是"通过"：

1. 自己运行的 `npm run check:full` 通过。
2. 没有一级和二级的问题。
3. 任务文件里的每一条都是"通过"，或者是"查不了"并且写明了为什么查不了。

- 拿不准是不是问题的，写进第六栏，不算进结论。
- 三级的问题记下来，不挡住通过。
- 不因为"差不多""大部分对了"而给通过。

### 5.9 不通过之后

写代码的助手按检查记录第五栏逐条修，提交，再叫检查员查一次（`第2次`）。检查员每次都从头查，不只看上次的问题。

同一步查了三次还没有通过，就停下来，把三份检查记录的文件名告诉项目负责人，不再自己修。

## 六、进度表

文件 `检查记录/进度表.md`，只有检查员能改。任务 01 到 09，分步的任务每一步一行：

| 任务 | 步 | 状态 | 查了几次 | 通过时的提交 | 留给项目负责人看的 |
|---|---|---|---|---|---|

状态只有四种：没开始、做完待查、不通过、通过。

## 七、对照效果图

`参考图/` 里是项目负责人确认过的效果图，`参考图/说明.md` 写了每一张是什么、哪些地方以文档为准。

`npm run shots` 做完截图之后，再生成一个网页 `过程截图/自动/对照.html`：左边是参考图，右边是对应的实际截图，一共四组。

| 参考图 | 对应的实际截图（1440 × 800） |
|---|---|
| `参考图/1-做决定.png` | `?demo=decide` |
| `参考图/2-弹窗.png` | `?demo=popup-bulk` |

这个网页是给人看的。检查员能看图片时，对照后写出差别最大的三处；"像不像、好不好看"由项目负责人决定。

## 八、演练：检查自己也要被检查

任务 01 做完自动检查和钩子之后，故意犯三次错，确认每一次都被拦住，然后恢复。把三次的真实输出贴出来。

| 故意做什么 | 应该看到什么 |
|---|---|
| 在 `src/engine/rng.ts` 里加一行 `Math.random()` | `npm run check` 在 K3 不通过（规则检查 R1）；`git commit` 不成功 |
| 把一条核对用例的测试改成 `.skip` | K4 和 K5 不通过 |
| 在 `docs/02-开发约定.md` 的末尾加一个字 | K1 不通过，并指出是这个文件 |

三次都恢复之后，`git status` 应该是干净的，`npm run check` 通过。

配了 3.2 的钩子的，再试一次：保留第一种错误，然后结束回答，看助手有没有被拦住并收到那句话。

## 九、检查员查不了的

| 查不了的 | 谁来看 |
|---|---|
| 好不好看、和效果图像不像 | 项目负责人，看 `对照.html` 和截图 |
| 看不看得懂、好不好玩 | 项目负责人试玩，找别人试玩（`docs/11` 第五节） |
| 数值平不平衡 | 文档的作者，看模拟报告 |
| 真实的数字对不对 | 项目负责人 |

检查员也是 AI，也会看错。所以它的每一个结论都要带证据，检查记录要留给项目负责人和文档的作者看。
