# 06 现金计划和季度报表

> 第 2 版（2026-11-20）。第 1 版的"三个 AI 员工提案"已经去掉，由本文代替。

这份文档规定：玩家做决定时能看到哪些参考数字和现金计划；每个季度结束时，财务报表怎么判断能不能进入下一个季度；提醒、"为什么"和"最关键的一个决定"怎么算。

**总原则：所有的决定都由玩家自己做。** 游戏不替玩家选，不给"该怎么做"的方案，也不在季度中间自己改玩家定好的数量。它只做两件事：把数字算清楚、摆在玩家面前；季度结束时如实结账。

代码放在 `src/plan/`，只能引用 `engine`、`params`、`products`。函数只输出编号和数字，文字放在 `src/text`。

## 一、三个功能区

玩家的决定按三个功能区来放。界面上三个功能区并排在前排（见 `docs/07` 第四节）。

| 代号 | 名字 | 管什么 | 对应的决定（`docs/04` 第 2.2 节） |
|---|---|---|---|
| `purchase` | 进货 | 货：库存、补货、路上的货、大单要的货 | `monthlyRestockQty` |
| `ops` | 运营 | 卖：售价、广告、零售订单、大单报价 | `priceSen`、`adBidFen`、`adDailyBudgetFen`、`bulkQuotes` |
| `finance` | 财务 | 钱：现金计划、货款、账单、风险 | `buyCompliance`、`upgradeToLocal` |

季度中间唯一要玩家选的事（大单货不够，`docs/04` 第十六节）属于进货区。

## 二、参考数字

每一个要填的数旁边都摆出参考数字。它们是事实和简单的估算，不是建议。

| 编号 | 是什么 | 怎么算 | 摆在哪 |
|---|---|---|---|
| `expMonthly` | 按上个季度和季节估算，这个季度每个月大约来多少零售订单 | 见下面 | 进货区、每月补货量旁边 |
| `stockDays` | 现在的库存够卖几天 | `expMonthly` 是 0 时为 0；否则 `Math.floor(Math.max(0, stockQty - reservedQty) * 30 / expMonthly)` | 进货区 |
| `lastMonthlyWanted` | 上个季度平均每月来了多少单 | `Math.floor(上个季度 quarterStats.wanted / 3)`；第 0 个季度没有 | 进货区 |
| `tierQty` | 拿到两档进货折扣要一次进多少件 | `moq * buyTier1Multiple`、`moq * buyTier2Multiple` | 每月补货量旁边 |
| `refPriceSen` | 市场上的普通售价 | 商品的 `refPriceSen` | 售价旁边 |
| `refBidFen` | 这个季度对手的广告出价 | `docs/04` 第四节，用季度第一天的值（对手出价没有每天的波动） | 广告出价旁边 |
| `bulkRefPriceSen` | 批发参考价 | 商品的 `bulkRefPriceSen` | 大单报价旁边 |
| `upgradeCostFen` | 现在升级成本土店要花多少 | `localSetupFeeFen + Math.ceil(stockQty * weightG * headHaulFenPerKg / 1000)` | 财务区 |

```
seasonNowBp(q) = applyBp(product.seasonBp[q % 4], q < 4 ? 10000 : year2DemandBp)

expMonthly =
  第 0 个季度：Math.floor(Math.floor(product.organicPerDayMilli * 30 / 1000) * seasonNowBp(0) / 10000)
  其他季度：  Math.floor(Math.floor(上个季度的 quarterStats.wanted / 3) * seasonNowBp(q) / seasonNowBp(q - 1))
```

`quarterStats` 在 `startQuarter` 的第 1 步才清零，所以季度第一天调用 `startQuarter` 之前，状态里的 `quarterStats` 就是上个季度的。

## 三、现金计划

做决定时，底部一直显示这个季度的现金计划（`docs/07` 第四节）。它回答一个问题：**照这个计划，最坏的时候（一单都没卖出去），季末还剩多少钱。**

```ts
interface CashPlan {
  startFen: number;          // 季初现金
  restockFen: number;        // 三次月初补货：3 * Math.min(monthlyRestockQty, supplierMonthlyCap) * costFen（按没有折扣的进价）
                             // 本土店（或这个季度升级成本土店）再加 3 * Math.ceil(同样的件数 * weightG * headHaulFenPerKg / 1000)
  fixedFen: number;          // 3 * monthlyFixedCostFen
  complianceFen: number;     // 本土店（或这个季度升级）并且 buyCompliance 时是 complianceCostFen，否则 0
  upgradeFen: number;        // 跨境直发并且 upgradeToLocal 时是 upgradeCostFen，否则 0
  sureOutFen: number;        // 上面四项之和。界面上叫"预计花掉"
  adsMaxFen: number;         // adDailyBudgetFen * 90。广告最多花掉多少
  sureInFen: number;         // 这个季度一定会到的钱，见下面
  worstEndFen: number;       // startFen + sureInFen - sureOutFen - adsMaxFen
}
```

"一定会到的钱"只算已经确定的两种：

1. 已经签收（`returnedQty` 不是 `null`）、还没到账的订单批次：`(qty - returnedQty) * payoutFenEach`，条件是 `Math.max(settleDay, payoutFrozenUntilDay)` 不晚于季末那天（`q * 90 + 89`）。
2. 已经交货（`status` 是 `"delivered"`）的大单：`valueFen - depositFen`，条件是 `balanceDay` 不晚于季末那天。

不算进去的（界面上用一行小字说明）：这个季度新卖出去的钱、新中标的定金、仓储费、大单运费、违约金、加急补货。

显示规则：

- `worstEndFen` 不小于 0：正常显示。
- `worstEndFen` 小于 0：用 `hibiscus` 色，旁边一句："如果这个季度一单都卖不出去，季末会差 {gap}。季末付不起，只能申请破产。"**不拦住玩家**，玩家可以照样进入这个季度。

## 四、季末结账和破产

`docs/04` 第 10.2 节第 11 步（第 3 版）的规定，这里再说一遍：

- 季度中间现金可以是负数。负数表示欠着供应商和平台的钱，先记着，季末一起结。
- 每个季度最后一天（`day % 90 === 89`）结束时，现金小于 0：这个季度付不起，`phase` 变成 `"bankrupt"`。
- 收尾阶段结束时（所有货款到账、所有大单结清），现金小于 0：`phase` 变成 `"bankrupt"`；否则是 `"finished"`。

季度报表（弹窗 P6）最后一栏是结账的结论，由 `settleVerdict(state)` 给出：

| 结论 | 条件 | 报表底部的按钮 |
|---|---|---|
| `continue` | `phase` 是 `"running"` | "确认报表"，之后主要按钮是"进入下一个季度" |
| `bankrupt` | `phase` 是 `"bankrupt"` | "申请破产"（只有这一个按钮）。点了之后去结局 |
| `banned` | `phase` 是 `"banned"` | "看结果" |
| `finished` | `phase` 是 `"finished"` | "看结果" |

## 五、季度报表的内容

季度报表就是 `docs/04` 第十七节的账单，加上下面这些。

| 部分 | 内容 | 函数 |
|---|---|---|
| 账单 | 按功能区分三块（进货、运营、财务），每块里按 `kind` 分行 | `buildQuarterBills`（`docs/04` 第十七节） |
| 核对 | 季初 + 收入 − 支出 = 季末 | `verifyQuarter` |
| 计划和实际 | 季初的现金计划（第三节）和实际的对比：预计花掉 / 实际花掉；广告最多 / 实际广告费；最坏的季末 / 实际季末 | `planVsActual(plan, bills, endCashFen)` |
| 带到下个季度的 | `carryOver` 的四样 | `carryOver`（`docs/04` 第十七节） |
| 这个季度的结果 | 零售发出、缺货；大单中了几张、交了几张；推流分和变化 | `quarterResult(q, events, startState, endState)` |
| 为什么 | 最多 3 句，见第六节 | `quarterCauses(...)` |
| 结论 | 第四节 | `settleVerdict(state)` |

`planVsActual` 的"实际花掉"是这个季度账单里 `restock`、`fixed`、`compliance`、`setup` 四种支出之和（取正数）；"实际广告费"是 `ads` 之和（取正数）。

## 六、为什么（最多 3 句）

按下面的顺序检查，条件成立就显示，满 3 句为止。只输出编号和数字。

| `key` | 条件 | 文字 |
|---|---|---|
| `cause_cash_negative` | 季末现金小于 0 | 季末现金是 {cash}，付不起。 |
| `cause_bulk_default` | 这个季度有大单违约 | 大单交不出货，赔了 {penalty}。 |
| `cause_audit` | 这个季度末被审核 | 风险到了"高"，平台冻结货款 {days} 天。 |
| `cause_rush` | 这个季度加急补过货 | 加急补了 {qty} 件，比平时多花 {extra}。 |
| `cause_stockout` | 这个季度缺货超过 5% | 缺货 {lost} 单，"近期发货水平"掉了 {pts} 分，下个月平台给的流量会变少。 |
| `cause_bulk_reserved` | 有货留给了大单，并且零售有缺货 | 有 {qty} 件货留给了大单，零售不够卖。 |
| `cause_ads_unspent` | 投了广告，实际花费不到预算的 60% | 广告预算只花掉 {pct}。出价比对手低，抢不到更多流量。 |
| `cause_ads_loss` | 每单的广告费高于每单的利润 | 广告每带来一单要花 {cost}，这一单只赚 {profit}。 |
| `cause_price_low` | 售价低于参考价 | 降价让"价格"多了 {pts} 分，但每单少赚 {diff}。 |
| `cause_price_high` | 售价高于参考价 | 涨价让每单多赚 {diff}，但"价格"少了 {pts} 分，买的人也少了。 |
| `cause_storage` | 本土店，仓储费里压货的部分大于 0 | 仓库里压着 {qty} 件卖不动的货，仓储费 {fee}。 |
| `cause_cash_wait` | 季末路上的货款大于现金 | 账上有 {cash}，还有 {pending} 在路上没到。 |
| `cause_push_up` | 推流分比上个季度高 5 分以上 | 推流分涨到 {score}，不花广告费的订单会变多。 |

## 八、最关键的一个决定

结局用（`docs/07` 第四节）。

1. 对玩家做过决定的每一个季度 `q`：把第 `q` 个季度的决定换成"参考做法"，其他季度保持玩家原来的决定，整局重算（季度中间的选择一律当作不处理）。
2. 净资产变化（绝对值）最大的那个季度就是最关键的。一样大时取靠前的季度。

参考做法只用来比较，不在做决定时显示成建议：

| 项 | 值 |
|---|---|
| `monthlyRestockQty` | `expMonthly` 是 0 时为 0；否则 `Math.min(supplierMonthlyCap, Math.max(moq, Math.ceil(expMonthly / 10) * 10))`。`expMonthly` 用重算到那个季度第一天时的状态 |
| `priceSen` | `refPriceSen` |
| `adBidFen`、`adDailyBudgetFen` | 0 |
| `bulkQuotes` | 不报 |
| `buyCompliance`、`upgradeToLocal` | `false` |

函数 `keyDecision(config, decisions, product, params)` 返回季度编号、玩家的净资产、换成参考做法后的净资产。

## 十、核对用例

### 10.1 参考数字

头巾，第 0 个季度，跨境直发。状态：`cashFen` 320000，`stockQty` 200，没有大单，售价 1990。

| 编号 | `expMonthly` | `stockDays` | `tierQty` | `refBidFen` | `upgradeCostFen` |
|---|---|---|---|---|---|
| R1 | 264 | 22 | 250、500 | 36 | 116000 |

### 10.2 现金计划

| 编号 | 状态 | 决定 | `restockFen` | `fixedFen` | `complianceFen` | `upgradeFen` | `sureOutFen` | `adsMaxFen` | `sureInFen` | `worstEndFen` |
|---|---|---|---|---|---|---|---|---|---|---|
| X1 | R1 的状态 | 补货 450，预算 6400 | 1215000 | 90000 | 0 | 0 | 1305000 | 576000 | 0 | -1561000 |
| X2 | 见下面 | 补货 100，预算 2000，做合规 | 294000 | 90000 | 60000 | 0 | 444000 | 180000 | 139467 | -234533 |
| X3 | R1 的状态 | 补货 0，预算 0，升级 | 0 | 90000 | 0 | 116000 | 206000 | 0 | 0 | 114000 |

X2 的状态：头巾，第 0 个季度，本土店，`cashFen` 250000，`stockQty` 100，`payoutFrozenUntilDay` 0。

- 订单批次 A：`qty` 10，`returnedQty` 1，`payoutFenEach` 2663，`settleDay` 30，`paid` false → 算 9 × 2663 = 23967。
- 订单批次 B：`qty` 5，`returnedQty` null（还没签收）→ 不算。
- 订单批次 C：`qty` 8，`returnedQty` 0，`payoutFenEach` 2663，`settleDay` 95 → 季末之后才到，不算。
- 大单：`status` "delivered"，`valueFen` 165000，`depositFen` 49500，`balanceDay` 60 → 算 115500。

X3：跨境直发，这个季度升级成本土店，补货是 0，所以没有头程运费。

### 10.3 结论

| 编号 | `phase` | 结论 |
|---|---|---|
| V1 | `"running"` | `continue` |
| V2 | `"bankrupt"` | `bankrupt` |
| V3 | `"banned"` | `banned` |
| V4 | `"finished"` | `finished` |

### 10.4 另外要测试

1. `cashPlan`：200 个种子、每个季度第一天的状态、随机的合法决定：`worstEndFen === startFen + sureInFen - sureOutFen - adsMaxFen`；除了 `startFen` 和 `worstEndFen`，各项不小于 0。
2. 同样的 200 局，真的跑完这个季度之后：实际花掉（第五节）不大于 `sureOutFen`；实际广告费不大于 `adsMaxFen`。
3. `keyDecision` 同一局算两次结果相同；换掉的那个季度之前，重算的每一天和原来完全一样。
4. `quarterCauses` 最多 3 条，顺序和第六节一样。
